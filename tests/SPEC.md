# 行为规格目录

这份目录是三个项目的行为契约。每条规格都有对应的可执行断言，
改代码时测试会直接告诉你哪条契约被动了，而不是等你上线后才发现。

## 怎么跑

```bash
python3 -m pytest                  # 全部，约 136 项，秒级
python3 -m pytest tests/specs      # 只跑确定性规格，不需要任何模型访问
python3 -m pytest tests/characterization
python3 -m pytest -m recorded      # 只跑录制回放
```

没有 `DASHSCOPE_API_KEY` 也能跑：规格层与特征层都用模型替身，
只有重新录制才需要真实访问。

## 两层测试各管什么

| | 规格层 | 特征层 |
|---|---|---|
| 位置 | `tests/specs/` | `tests/characterization/` |
| 是否涉及模型 | 否 | 是，用脚本化替身或录制回放 |
| 回答的问题 | 这个功能是什么 | 这条链路现在怎么走 |
| 重构时 | 几乎不用改 | 兜底用，防止行为漂移 |

规格层是「应该如此」的契约，特征层是「目前如此」的快照。
两者分开，是因为重构会改实现，但不该改契约；而特征层能告诉你实现有没有跑偏。

## 模型怎么被替换掉

`tests/fakes.py` 里的 `FakeClient` 按脚本逐条返回预设文本，
`conftest.py` 的 `llm` fixture 把它装到 `warehouse_data._build_client` 上。

三个项目都用 `import warehouse_data as wd` 加 `wd.xxx()` 的形式访问模型入口，
所以替换一处就够了。这也是当初把 `from warehouse_data import _build_client`
改成模块引用的原因——后者在导入时就绑定了函数对象，替换对其无效。

```python
client = llm(["第一条响应", "第二条响应"])
# 跑完链路后
assert client.call_count == 2            # 模型被调了几次
assert "Observation" in client.requests[1][0]["content"]   # 第二轮看到了工具结果
```

脚本用尽时 `FakeClient` 会抛错，于是「实际调用次数超出预期」会立刻暴露，
而不是静默返回空串把问题藏起来。

## 规格清单

### 一、域数据的结构与自洽性　`test_data_spec.py`

| 规格 | 要点 |
|---|---|
| 空间树规模 | 5 个库房、8 个库区、14 组密集架 |
| 低氧库区架位 | 固定为 `3-2-LO-01`、`3-2-LO-02`，是多个用例的落点 |
| 能源环境与空间树对应 | `STORAGE_ENV` 的键与空间树库房一一对应，不多不少 |
| 能耗汇总自洽 | 全楼 122.9 / 3452.9 必须等于各库房之和，不是独立维护的数字 |
| 环境告警唯一 | 当前只有 3楼2号库房 湿度 62.8% 越界 |
| 设备台账 | 11 台、编号唯一、挂载位置真实存在 |
| 设备离线状态 | 离线设备恰好是 2楼1号库房断路器 |
| 档案台账 | 8 条、档号唯一、架位真实存在、四类齐全 |
| 可控类型 | 只有断路器与门禁，动作各两个 |

### 二、六个工具的输入输出　`test_tools_spec.py`

响应码是契约的一部分，不是实现细节：

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 4000 | 缺少必要参数 |
| 4001 | 设备类型不支持远程控制，或模式类动作 |
| 4003 | 设备离线，指令未下发 |
| 4004 | 目标不存在，附可选范围 |
| 4006 | 两个检索条件互斥 |

覆盖：场景解析命中与未命中、设备按类型过滤、可控标记与支持的动作、
在线设备控制成功、离线设备拒绝、不可控类型拒绝、模式类动作拒绝、
档案按题名与按类型检索、两条件互斥、能耗汇总与未登记、环境告警与正常。

### 三、知识边界　`test_scope_spec.py`

两个方向都要锁：越界话题必须命中，领域内问题绝不误伤。

误伤比漏拦更危险——一旦领域内的问题被拦下，用户就再也拿不到答案了。

### 四、ReAct 解析协议　`test_parser_spec.py`

| 规格 | 要点 |
|---|---|
| 认得出 | Final Answer、Action + Action Input、中文冒号 |
| 认得出变体 | 加粗标记、代码围栏、单参数标量回退 |
| 认不出就抛错 | 无动作无答案、缺 Action Input、Final Answer 为空、非法 JSON |
| 抛错带原文 | 否则没法区分是提示词问题还是模型问题 |
| 只认 ASCII 工具名 | 中文工具名会被判为无法解析，这是当前实现的边界 |

### 五、协调层三元组　`test_coordinator_spec.py`

每次输出必须同时给出查询类型、处理模式、优先级。
认得出变体（代码围栏、前后缀文字、任意键序），
取值不合法或缺字段一律抛错，**不设默认值兜底**。

路由分错比报错更危险：默认走反应式会让本该深入分析的请求草草收场，
而且这种偏差很难被察觉。

### 六、两张状态图的结构　`test_graph_spec.py`

| 项目 | 形状 |
|---|---|
| 混合式 | 7 个节点，协调层一次分派两条分支，深思熟虑侧是收集→分析→建议三段，两条分支汇到同一个出口 |
| 深思熟虑 | 5 个节点严格线性，每个节点恰好一条出边 |

线性是深思熟虑的特征，不是漏写了分支。

### 七、提示词与调用参数　`test_prompt_spec.py`

两步锁住：占位符集合等于期望集合，再用占位值渲染一遍验证自洽。
另外锁住边界条款必须写进提示词——工具层兜底挡不住模型自己编造。

## 特征清单

### 反应式执行循环　`test_react_flow.py`

两轮闭环、无需工具时直接回答、观察回灌下一轮、
未知工具回灌提示让模型自纠、轮次上限抛错、
越界问题一次模型调用都不发生、解析不出就抛错。

### 混合式两条分支　`test_hybrid_flow.py`

反应式分支走模型循环、深思熟虑分支走满三段且顺序正确、
答复取自建议节点而非分析节点、优先级传进建议提示词但不参与分支、
协调层输出非法即抛错、越界不进图、反应式分支有轮次上限。

### 深思熟虑五阶段　`test_deliberative_flow.py`

感知阶段真调工具且不调模型、五阶段共四次模型调用、
上一阶段产出进入下一阶段提示词、越界不进流水线。

其中一条如实记录了当前薄弱点：四阶段全返回空时产出空报告而不报错。
若后续改成显式抛错，那条测试会失败并提醒确认。

### 录制回放　`test_recorded.py`

录制件由 `python tests/record.py` 采集并随代码入库，四个场景：
反应式定位、混合式简单查询、混合式跨库房对比、深思熟虑报告。

回放时不联网、不消耗额度，只断言结构事实：不抛异常、调用次数、
产出里出现真实采集到的数据。不做逐字比对——同一个问题模型每次措辞都不同，
逐字比对只会得到脆弱的测试。

模型版本变了就重新录一次。

## 加一条新规格时

1. 先问「这是契约还是快照」。确定性、不由模型决定的，放 `specs/`；
   依赖模型的，放 `characterization/`。
2. 测试名写成 `test_<主体>_should_<行为>_when_<条件>`，读名字就知道锁的是什么。
3. 跑一遍确认是绿的，再把断言收紧——先记录现状，再谈期望。
